# Suivi de préparation Supabase — projet de test

L'état ci-dessous repose sur les retours de l'utilisateur dans la conversation, pas sur un accès direct ou une vérification indépendante du projet. L'utilisateur indique que les données sont fictives. Référence de projet : `bbhocbfcjhccabqkngxt`.

- Le projet avait les tables Rawdha+ historiques, sans entrée d'historique de migrations pour les versions à partir de `20261108090000` ; les exécutions manuelles via SQL Editor ne sont pas automatiquement enregistrées dans cet historique.
- L'utilisateur a exécuté les SQL de `20261108090000` et `20261108100000`, en ajoutant avant cette dernière la mise en `pending` d'une directrice de test dont le statut était absent. Il a ensuite installé manuellement onboarding `20261108270000`, la nouvelle initialisation inscription `20261108370000` et le hook `20261108110000`.
- L'utilisateur dit avoir mis à jour l'Edge Function `register-director-request` avec la version fournie. Un test Supabase avec une identité fictive a renvoyé HTTP 201 `active` ; une requête de vérification a montré statut approuvé, abonnement actif, onboarding préparé et `director_email_verification.verified_at` null. Aucun essai de connexion client réel n'a encore été effectué. Auth marque néanmoins l'e-mail confirmé sans preuve ; aucun mécanisme de vérification différée n'est encore connecté. La limite globale de tentatives n'est pas une protection complète.
- `20261108120000` puis `20261108130000` exécutées. Avant la seconde, l'utilisateur a approuvé la mise à l'écart d'une présence de test orpheline ; l'original a été copié dans `public.rawdha_test_presence_backup`, table privée dont les droits ont été révoqués. Cette sauvegarde ne comporte ni politique de rétention ni purge automatique.
- Les migrations `20261108140000` à `20261108160000` ont été groupées en une transaction et l'utilisateur rapporte leur succès.
- Les migrations `20261108170000` à `20261108220000` ont été groupées en une transaction. Un premier essai a échoué sur deux factures orphelines. Après accord de l'utilisateur, elles ont été copiées dans `public.rawdha_test_factures_backup` (table privée sans purge automatique) puis supprimées ; le second essai a réussi d'après l'utilisateur. L'utilisateur n'a pas demandé d'effacer d'autres données.
- Les migrations `20261108230000` et `20261108240000` parents/abonnements, puis `20261108250000`, `20261108260000` et `20261108280000` à `20261108360000` ont été groupées et exécutées d'après l'utilisateur. Les fonctions parents sont accessibles sans connexion et ne doivent pas recevoir de vraies données sans audit ; l'intégration SlickPay réelle reste non vérifiée.
- Après confirmation explicite de l'utilisateur, l'identifiant du compte admin identifié comme le sien a été ajouté à `identity_super_admins` via SQL. L'utilisateur rapporte le succès. Il indique aussi avoir créé et déployé l'Edge Function `identity-document-review` avec le code fourni. Le worker OCR autonome n'est pas hébergé ni configuré, et la fonction n'a pas encore été testée sur cet environnement.
- L'utilisateur indique avoir déployé `send-parent-web-push`, puis `slickpay-checkout` et `slickpay-webhook` avec les versions fournies. La fonction de retour de paiement doit être accessible sans JWT ; son réglage effectif n'a pas été vérifié. Les versions SlickPay exigent une activation explicite et un environnement configuré, mais l'état réel des secrets est inconnu. Paiements, clés VAPID et push réels non vérifiés.

- Le traitement OCR local sur l'appareil du super admin est préparé dans le client non déployé. Il n'a pas besoin du worker serveur ; il ne sauvegarde pas le résultat OCR. Le navigateur reçoit les modèles depuis l'origine de l'application et récupère la carte depuis Supabase. Une mise à jour de l'Edge Function `identity-document-review` en réponse binaire est indispensable : la version précédemment déployée envoyait `image/png` ou `image/jpeg`, interprétés comme texte par le client Supabase. Les essais locaux avec cartes fictives sont réussis ; la correction Edge et le client ne sont pas encore déployés.


Avant un lancement réel : identifier et rapprocher l'historique de migrations avec les changements manuels, sauvegarder et tester la restauration, revoir toutes les politiques et services exposés, examiner la sécurité de l'inscription et du portail parent, mettre en place la vérification d'email et les protections anti-abus, déployer et tester le client correspondant ainsi que les autres fonctions requises. L'accès au statut super admin, les paiements, les push et la lecture OCR ne doivent pas être considérés comme validés sans essais de bout en bout. Ne pas pousser GitHub sans accord.
